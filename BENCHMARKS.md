# Benchmarks

Measured results for TimberStat's scanning engine. Every number below is copied from a
raw output file under `benchmarks/results/` or from a Criterion run whose output is saved
in the same session directory. No number is taken from memory or from another machine.
The method is in [`benchmarks/README.md`](benchmarks/README.md); the rules are in
[`docs/PERFORMANCE_PLAN.md`](docs/PERFORMANCE_PLAN.md).

## Status

- **Measured:** generic (`std::fs`) scanner on Windows, warm cache: wall time,
  entries per second and peak working set on six synthetic datasets; Criterion
  microbenchmarks of the scanner and of tree aggregation; the ignored 100k scanner test.
- **Not measured:** cold cache, the NTFS MFT scanner, Linux, treemap and radial
  generation, rendering, search latency, hashing, file-operation throughput and UI
  responsiveness. See [Not measured](#not-measured).
- **Single machine.** Nothing here is a cross-machine claim.

## Datasets

Generated by `gen-dataset` under `%TEMP%\timberstat-bench-<id>`. Each has a manifest
with the expected node count; every scan matched its manifest.

| Id | Shape | Files | Folders | Tree nodes (incl. root) | Max depth |
|---|---|---:|---:|---:|---:|
| `small` | flat, 0-4 KiB | 300 | 1 | 302 | 1 |
| `deep` | 220 nested folders, 2 files of 32 B each | 440 | 220 | 661 | 220 |
| `many-small` | 20 folders x 1000 files, 0-4 KiB | 20 000 | 20 | 20 021 | 1 |
| `100k` | 100 folders x 1000 files, 16 B each | 100 000 | 100 | 100 101 | 1 |
| `few-huge` | 4 files of 1 GiB logical length | 4 | 1 | 6 | 1 |
| `1m` | 1000 folders x 1000 files, 0-4 KiB | 1 000 000 | 1 000 | 1 001 001 | 1 |

`few-huge` sets logical length only; the manifest records logical bytes. Generating `1m`
took 22 min 6 s (`gen-dataset` run, real time). `few-huge` took 0.15 s.

**Cross-session spread.** A second session with the sampler off, run later on the same

## Peak working set: generic scanner, warm cache

Session `measured-20261127T172823Z` (sampler on). Each sample is a fresh process. Peak is
the highest working set sampled every 2 ms, so it is a **lower bound** on the OS peak. The
wall times from this session are inflated by the sampler and are not used above.

| Dataset | Median peak (MiB) | Min - max (MiB) |
|---|---:|---:|
| small | 9.37 | 9.34 - 9.55 |
| deep | 10.71 | 10.46 - 10.79 |
| many-small | 14.04 | 13.55 - 15.09 |
| 100k | 31.06 | 30.66 - 32.41 |
| few-huge | 9.29 | 8.76 - 9.31 |
| 1m | 225.06 | 220.90 - 299.61 |

Sampler overhead was not isolated. Sampler on vs off gave, for `100k`, 55.22 ms vs
35.74 / 53.34 ms, and for `many-small`, 34.02 ms vs 12.28 / 32.97 ms. Those pairs
overlap across sessions, so no overhead figure is claimed.

## Nightly scale test: `hundred_thousand_files_scan` (ignored)

`cargo test -p timberstat-scanner --release --test scan -- --ignored --exact hundred_thousand_files_scan --nocapture`

Output `benchmarks/results/measured-20261127T172823Z/scale-100k-ignored-test.txt`:
`scanned 100000 files in 1.1836844s`. The test passed. The full test took 149.76 s,
almost all of it creating the 100 000 files before the timed scan. The nightly workflow
(`.github/workflows/nightly-perf.yml`) runs the same command on a GitHub-hosted Linux
runner, which is a different machine. Its results are not comparable with the table above.

## Reproducing

```sh
cargo build -p timberstat-perf --release --bins
cargo run -p timberstat-perf --release --bin gen-dataset -- small deep many-small 100k few-huge
PERF_SCAN=target/release/perf-scan bash benchmarks/run-macro.sh -n 5 -m off small deep many-small 100k few-huge
PERF_SCAN=target/release/perf-scan bash benchmarks/run-macro.sh -n 5 small deep many-small 100k few-huge
cargo bench -p timberstat-perf
```

Re-runs write new directories under `benchmarks/results/` with a fresh stamp. Do not edit
the numbers above from memory: copy them from the new `summary.json`.

## Changes made to the method while measuring

- The first timing session ran with the working-set sampler on. It was kept, but its
  wall times are not used. The `-m off` sessions were run to get timing without the
  sampler.
- The Criterion `tree_rollup` bench panicked on its first run (a file was used as a
  parent). It was fixed in the bench, and the reported run is the fixed one.
